# Q10: pi-subagents Model Identifiers and Tier Designations

## Summary
pi-subagents supports two forms of model identifier in the `model` frontmatter field: full `provider/modelId` strings and fuzzy tier names like `"haiku"` and `"sonnet"`. There is no explicit `"inherit"` keyword — omitting the field entirely inherits the parent agent's model. Model resolution uses a fuzzy substring matcher against pi's model registry, with frontmatter values taking authoritative precedence over tool-call parameters.

## Supported Model Identifier Strings

| Form | Example | Tier Mapping |
|------|---------|-------------|
| Full `provider/modelId` | `anthropic/claude-haiku-4-5-20251001` | Exact match to haiku-tier; must be available (auth configured) |
| Full `provider/modelId` | `anthropic/claude-sonnet-4-6` | Exact match to sonnet-tier; must be available |
| Fuzzy tier shorthand | `"haiku"` | Fuzzy substring match — matches any available model whose `id` or `name` contains "haiku" |
| Fuzzy tier shorthand | `"sonnet"` | Fuzzy substring match — matches any available model whose `id` or `name` contains "sonnet" |
| Omitted / undefined | *(no model field)* | Inherits parent agent's model |

There is **no hardcoded tier→model mapping table** in pi-subagents. The fuzzy matcher scores against whatever models pi's registry makes available. A score >= 20 (out of 100) is required.
- Source: `src/model-resolver.ts:1-71` — `resolveModel()` function

## Shorthand Tier Names vs Full Model IDs
The frontmatter `model` field **does accept shorthand tier names** (`"haiku"`, `"sonnet"`). README: "model — provider/modelId or fuzzy name ("haiku", "sonnet")". The `Agent` tool parameter description: `"Optional model override. Accepts \"provider/modelId\" or fuzzy name (e.g. \"haiku\", \"sonnet\")."`

In the default `Explore` agent config, model is specified as a full ID: `model: "anthropic/claude-haiku-4-5-20251001"` (`src/default-agents.ts:38`). README describes this as `"haiku (falls back to inherit)"`.

## Model Resolution at Dispatch Time (Parent-Agent Inheritance vs. Explicit Override)

Three-tier priority:
1. **Agent config frontmatter `model`** (highest priority) — if `.md` file specifies `model`, it locks. Resolution failure → silent fallback to parent.
2. **Agent tool-call `model` parameter** — used only if config frontmatter does NOT specify. Resolution failure → error shown to user.
3. **Parent agent's model** — used when neither config nor params specify.

Precedence logic in `src/invocation-config.ts:13-30`:
```
modelInput: agentConfig?.model ?? params.model,
```
Frontmatter-authoritative contract: frontmatter values take precedence over Agent tool-call parameters (CHANGELOG v0.5.1).

## Special Model Values ("inherit" / "default")
There are **no literal keyword values** like `"inherit"` or `"default"`. Inheritance works by omission:
- When agent config has no `model` field AND tool call omits `model` → `modelInput` is `undefined` → stays as `ctx.model` (parent's model).
- `general-purpose` default agent has no `model` field, so it always inherits parent's model.
- Source: `src/default-agents.ts:14-29`; `src/invocation-config.ts:28`

## Mechanism for Translating Identifiers to LLM API Calls
pi-subagents does **not** make direct API calls. Resolution path:
1. `resolveModel()` in `model-resolver.ts` maps string → `Model` object via `registry.find(provider, modelId)`
2. Resolved `Model` passed as `options.model` to `AgentManager.spawn()` / `spawnAndWait()`
3. AgentManager passes through to `runAgent()` (`src/agent-runner.ts`)
4. `runAgent()` passes to `createAgentSession()` (`src/agent-runner.ts:185-194`)
5. Session infrastructure handles all subsequent API communication
