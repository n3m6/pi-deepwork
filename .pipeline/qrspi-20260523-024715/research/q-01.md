# Q1: Deepwork Pipeline Stages, Route Determination, Backward Loop Protocol, and State.md Schema

## Summary
The deepwork orchestrator implements a 10-stage pipeline (Goals → Questions → Research → Design → Structure → Plan → Implement → Accept-Test → Replan → Verify → Report). Stage 1 determines `full` vs `quick-fix` route. A backward-loop protocol handles mid-pipeline redirection triggered by Stages 7, 8, and 8.5. All recovery state is persisted in a YAML-frontmatter `state.md` with 10 defined fields.

## Stage responsibilities and leaf subagents dispatched

Defined in the architecture table at `deepwork.md:112-124`:

- **Stage 1** — captures intent, requirements, acceptance criteria; dispatches `qrspi-goals-synthesizer`; has a human gate.
- **Stage 2** — generates tagged research questions; dispatches `qrspi-question-generator`, `qrspi-question-leakage-reviewer`, `qrspi-question-quality-reviewer`.
- **Stage 3** — per-question findings and unified summary; dispatches `qrspi-codebase-researcher`, `qrspi-web-researcher`, `qrspi-research-synthesizer`, `qrspi-research-reviewer`.
- **Stage 4** — architecture, vertical slices, test strategy; dispatches `qrspi-design-synthesizer`, `qrspi-design-reviewer`; has a human gate.
- **Stage 5** — file mapping, interfaces, create/modify; dispatches `qrspi-structure-mapper`, `qrspi-structure-reviewer`; has a human gate.
- **Stage 6** — overall plan, task specs, baseline; dispatches `qrspi-plan-writer`, `qrspi-task-spec-writer`, `qrspi-task-spec-reviewer`, `qrspi-plan-reviewer`, `qrspi-baseline-checker`.
- **Stage 7** — phased TDD implementation via per-task/wave fast-impl loops; dispatches `qrspi-fast-impl-loop` (which sequences code → test → verify), `qrspi-e2e-regression-checker`, `qrspi-integration-checker`, `qrspi-baseline-regression-checker`, `qrspi-simplify-pass` (post-wave).
- **Stage 8** — acceptance testing and backward-loop detection; dispatches `qrspi-acceptance-tester` (which in turn dispatches coverage planner, traceability reviewer, spec reviewer, code quality reviewer, and `build`), `qrspi-backward-loop-detector`.
- **Stage 8.5** — replanning remaining work across phases; dispatches `qrspi-replan-writer`, `qrspi-replan-reviewer`.
- **Stage 9** — final verification gate; dispatches `qrspi-verifier`.
- **Stage 10** — final report; dispatches `qrspi-reporter`.

## Route Determination

The route is determined during **Stage 1 (Goals)** by the `qrspi-goals` subagent, returned in the `### Route` field, and written to `config.md` (`deepwork.md:472`). The two routes:

- **`full`**: features, new products, architectural changes, multi-file changes requiring design alignment; may be single-phase or multi-phase.
- **`quick-fix`**: bug fixes, small targeted changes, estimated 1-3 file modifications; always single-phase.

These definitions are at `deepwork.md:474-475`. Route change is allowed before Stage 6 (Plan) executes; after Plan completes, the route is locked (`deepwork.md:477`, `deepwork.md:690`).

**Quick-fix consequences** (at `deepwork.md:596`, `deepwork.md:619`):
- Stage 4 (Design) is skipped.
- Stage 5 (Structure) is skipped.
- Stage 8.5 (Replan) is skipped.
- Single-phase with `total_phases: 1` and no per-phase loop.

**Phase handling** (`deepwork.md:479-483`): Full route reads phase count from `phase-manifest.md` after Stage 6. Single-phase full runs skip Replan. Multi-phase full runs cycle Stage 7 → Stage 8 → Stage 8.5 repeatedly until the final phase, then enter Stage 9.

## Per-Phase Loop

The per-phase loop is defined in the diagram at `deepwork.md:81-87`: Implement (7) → Accept-Test (8) → Replan (8.5) — repeating until the final phase is complete.

The transition logic is at `deepwork.md:775-776`: after Stage 8, if quick-fix, total_phases=1, or current phase is final → proceed to Stage 9; otherwise proceed to Stage 8.5. After Stage 8.5, if more phases remain → re-enter Stage 7; otherwise proceed to Stage 9 (`deepwork.md:827-832`).

## The Backward Loop Protocol

Triggered when any of three stage subagents returns a `### Backward Loop Request` section:
- `qrspi-implement` (`deepwork.md:727`)
- `qrspi-accept` (`deepwork.md:766`)
- `qrspi-replan` (`deepwork.md:810`)

The protocol itself is defined at `deepwork.md:887-896`:
1. Emit `stage.failed` telemetry event.
2. Emit `backward_loop.requested` telemetry event.
3. Regenerate `telemetry/run-log.md`.
4. Read `protocol/deepwork-backward-loop-protocol.md` with `cat`.
5. Follow that protocol using current route, phase, and request details.
6. Present a user decision gate (`gate.presented` → `gate.approved` with `context.gate: "backward-loop-decision"`), emit `backward_loop.decided` (or `.deferred` for option D, or `.reset` for option G) with the decision choice.

**Unclean-cap escalation gates** (user-prompted backward loops from inside a stage):
- **Stage 6 (Plan)**: at `deepwork.md:669-678`. Options: A) Continue, B) Loop back to Stage 5 (Structure) — full only, C) Loop back to Stage 4 (Design) — full only, D) Loop back to Stage 1 (Goals).
- **Stage 8.5 (Replan)**: at `deepwork.md:813-822`. Options: A) Continue, B) Loop back to Stage 5 (Structure), C) Loop back to Stage 4 (Design), D) Loop back to Stage 1 (Goals).

**Stage 9 auto-fix route** (not a user-visible backward loop, but an automatic Stage 7 re-entry): at `deepwork.md:850-858`. On Stage 9 FAIL, `qrspi-implement` is re-dispatched in `verify-fix` mode; if that succeeds, re-dispatch Stage 9; if Stage 9 fails a second time, invoke the backward loop protocol.

## The `state.md` YAML Schema

Defined at `deepwork.md:321-340` and `deepwork.md:353-381`. Fields:

| Field | Type | Description | Default |
|-------|------|-------------|---------|
| `run_id` | string | `qrspi-YYYYMMDD-HHMMSS` | generated in Pre-Flight |
| `route` | string | `full` or `quick-fix` | `unknown` until Stage 1 |
| `current_phase` | integer | Current active phase number | `1` |
| `total_phases` | integer | Phase count from `phase-manifest.md` | `1` for quick-fix, `0` until Plan |
| `last_completed_stage` | string | Last completed stage name (or `none`) | `none` initially |
| `next_stage` | string | Next stage to dispatch | `goals` initially |
| `stages_completed` | list of strings | All completed stage names | `[]` |
| `phase_history` | list of objects | Per-phase `{phase, completed_stages}` entries | `[]` |
| `backward_loops` | integer | Count of backward loops | `0` |
| `resume_source` | string | `state`, `artifacts`, or `fresh` | `fresh` |

Runtime rules (`deepwork.md:342-351`):
- `current_phase` stays `1` until `phase-manifest.md` exists.
- `total_phases` is `1` for quick-fix, `0` for full until Plan produces `phase-manifest.md`.
- Phase directory names are zero-padded: `phases/phase-01`, `phases/phase-02`, etc.
- `resume_source`: `fresh` for new runs, `state` when recovered from `state.md`, `artifacts` when reconstructed from disk.
- `stages_completed` may include `replan` once at least one phase transition completes.
- `phase_history` records per-phase stage-boundary completion.
- `state.md` is a stage-boundary checkpoint only; mid-stage interruption restarts that stage from its beginning.

**Write rules**: `state.md` is overwritten by deepwork after Pre-Flight, after every successful stage transition, after every backward-loop routing decision, and after every resume recovery decision (`deepwork.md:319`).
